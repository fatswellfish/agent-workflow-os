## 解决的问题

大多数人用 AI Agent 就像用一个特别聪明的聊天框。能用，直到不能用：

- 你说过的事，下周它就不记得了
- 你纠正了一次，这个纠正扩散到它不该碰的地方
- 它"记得"三个月前的端口号，还很自信地用错
- 你的指令、你的 skill、你的笔记各说各话，没人知道哪个是真的

这套架构来自**反复撞墙**：一台本地 GPU 集群、一条媒体生产线、一条软件流水线、一个家庭档案库，全部由一个 agent 驱动。

它不是框架，是一组**习惯、边界和一个校验脚本** —— 让一个庞大的指令系统不至于腐烂。

## 核心思想一：Agent 有三层记忆，且不可互换

| 层 | 放什么 | 何时加载 | 成本 |
|---|---|---|---|
| **记忆** | 怎么**想**。行为准则。 | 每轮，永远 | 每轮都付 |
| **Skill** | 怎么**做**某件具体的事。流程、脚本、坑。 | 触发时才加载 | 按任务付 |
| **知识库** | 发生了**什么**。事实、决策、历史。 | 搜索时才读 | 按查询付 |

由此得出：

> **记忆存"怎么想"，Skill 存"怎么做"，知识库存"发生过什么"。**

以及一条能提前消灭大部分一致性问题的硬约束：

> **易变的事实（端口、路径、模型名、版本号）绝不进记忆。
> 记忆里只放指向单一事实源的指针。**

**原因**：记忆每一轮都被注入。一个高变更率的事实待在高注入通道里，是灾难组合——你改了文件，但所有**已经在进行的对话**仍然持有旧值，而用户没有理由去重开会话。

这和业界独立收敛到的架构一致（参见 [CoALA](https://arxiv.org/abs/2309.02427)：working / episodic / semantic / procedural），也能干净地映射到 Claude Skills、CLAUDE.md、MCP 三者的分工。

## 核心思想二：索引是指针，而指针会腐化

常见的失效：索引里写着"这类任务加载 `media-pipeline`"，但 `media-pipeline` 从没创建过，或者两个月前改名了。

**危险的不是它失败，是它静默失败**：agent 加载不到，于是用自己的通用知识临场发挥，产出看着还挺合理。

我们一次审计中发现了 **7 个索引 skill 里 27 处这样的死链**。

解法不是纪律，是脚本：

```bash
python scripts/benchmark.py --skills <skills目录> --memory <记忆文件> --kb <知识库>
```

任何索引指向不存在的 skill，就报错。端口号、模型名、记忆体积同理。

## 核心思想三：确定性是免费的，推理不是

> 机械任务 → 脚本。主观分析 → 模型。

验证一个 skill 名字是否存在、文档里的端口是否和部署台账一致、文件名是否符合约定——这些都是**确定性检查**。
用 LLM 做要花 token 且有方差，用 Python 做不要钱且永远不会累。

Red Hat 的 AI 工程团队测出这个拆分能**降低 26% 成本**。对我们来说重点不在成本，而在于**脚本不会"忘记"去检查**。

## 实测数据

在真实系统上（1,867 份知识库文档、138 个 skill、9 个索引文件）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| **索引死链** | **27** | **0** |
| **记忆里的易变事实** | **3** | **0** |
| **跨文档事实冲突** | **3** | **0** |

三类问题全部归零。**没有一个是靠"更小心一点"修好的**——每一个都是靠一个会运行的检查。

## 适合谁

- 你在用**一个** agent 干好几类真不一样的工作（写作、编程、媒体、运维），指令面已经膨胀到手记不下了
- 你已经被"agent 自信地使用过期事实"坑过
- 你在考虑把一个 agent 拆成好几个专精的——想知道这到底是不是正确的选择（剧透：通常不是，见 `docs/03`）

## 不适合谁

- 单一用途的 agent，这套开销不值
- 还没有共享配置事实源的团队——先解决那个

## 状态

从在用的系统里提炼出来的，不是纸上写的。`scripts/` 里每一样都能跑。`docs/` 里每一个选择都对应一次真实失败，并且写明了失败是什么。

随底层系统演进持续维护——结构可能会变，原则不应该。
